# P1.2 Workflow 生命周期工作台

## 本轮回归修复

基于本地 `WorkflowLifecycle.test.ts` 反馈，生命周期工作台此前虽然已从真实 `Workflow` API 获取工作流，但选择器区域只展示技术 ID，没有把 `Workflow.name` 渲染为当前工作流身份信息，导致真实数据场景下页面无法确认当前上下文，测试因此无法找到 `订单审批`。

本轮将后端返回的 `Workflow.name` 作为选择器旁的主身份文本，同时保留 `workflow_id` 作为诊断标识；响应式窄屏下身份信息独占一行，避免工作流名称、选择器和状态标签互相挤压。

测试 Stub 同步注册 `v-loading` 指令，消除 Element Plus 指令在单元测试环境中的非业务警告，使测试输出更接近真实组件注册环境。

## Contract 对齐

当前前端仍只使用正式 `workflowApi` Contract：

- `GET /workflows`
- `GET /workflows/{id}/versions`
- `GET /workflows/{id}/triggers`
- `GET /workflows/{id}/triggers/{trigger_id}/schedule`
- `GET /workflows/{id}/executions`

工作流名称直接来自 `Workflow.name`；不得在前端根据 ID 或其他字段推断名称。Runtime 跳转继续使用真实 `execution_id`、`workflow_id`、`workflow_version_id`。

## 验收范围

- 正常数据：显示工作流名称、生命周期阶段、当前生效版本、最近 Execution。
- Empty：无工作流时显示明确中文下一步提示。
- Runtime 深链：从最近 Execution 进入 Runtime 时保留真实执行上下文。
- Loading：测试环境显式注册 `v-loading` 指令，避免测试噪声。
- 响应式：窄屏下工作流身份信息与选择器自适应换行。

## 本地测试记录

用户提供的最新本地反馈为：`WorkflowLifecycle.test.ts` 3 个测试中 2 个通过、1 个失败；失败原因是页面未渲染 `Workflow.name`，同时存在 `Failed to resolve directive: loading` 警告。

本轮代码已针对上述两个问题完成修复，但当前执行环境无法直接访问用户 Windows 本地工作区，因此不能将未实际执行的 `npm test`、`npm run build` 或 Frontend Gate 标记为通过。开发者应在同步后的 `frontend` 分支执行：

```powershell
npm ci
npm test -- tests/views/WorkflowLifecycle.test.ts
npm test
npm run build
npm run test:gate
```

若 `npm ci` 再次出现 `@esbuild/.win32-x64-*/esbuild.exe` 的 `EPERM unlink`，先关闭占用该文件的 Node/Vite/编辑器进程并确认安全软件未锁定文件，再重新执行依赖安装；不得使用 `npx vitest` 临时下载依赖绕过项目锁定版本。
