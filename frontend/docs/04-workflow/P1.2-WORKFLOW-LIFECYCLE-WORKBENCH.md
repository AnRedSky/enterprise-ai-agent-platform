# P1.2 Workflow 生命周期工作台

## 目标

本切片把已经由后端提供的 Workflow、Version、Trigger、Scheduler、Execution 事实集中到一个只读治理工作台，避免用户在多个页面之间拼接生命周期状态。

## 后端 Contract 对齐

前端只读取 `workflowApi` 已存在的正式接口：

- `GET /workflows`
- `GET /workflows/{id}/versions`
- `GET /workflows/{id}/triggers`
- `GET /workflows/{id}/triggers/{trigger_id}/schedule`
- `GET /workflows/{id}/executions`

不在前端推断 Trigger → Execution、调度结果或发布关系；当前生效版本直接以 `published_version_id` 与版本 `id` 对齐，Scheduler 数据直接展示后端返回的 `next_run_at`、`last_run_at`、`last_execution_id`。

## 交互设计

1. 默认选择第一个工作流，减少进入页面后的空操作。
2. 生命周期阶段按“工作流 → 版本 → 发布 → 触发器 → 运行”展示，状态来自真实数据。
3. 定时 Trigger 才请求 Scheduler 状态，其他 Trigger 不产生无意义请求。
4. 版本、Trigger、Execution 采用并行请求；Scheduler 仅针对定时 Trigger 批量按需查询。
5. 归档工作流保持可观测，但明确提示只读，不增加前端伪造的变更能力。
6. 未知状态保留技术标识，例如 `未知状态（waiting_for_approval）`，避免后端新增枚举导致 UI 静默丢失信息。

## 错误与安全

- 后端错误不直接展示原始 HTTP / exception 文本。
- 前端不展示 Secret；Webhook 的敏感配置继续由现有 Trigger 页面治理。
- Tenant / owner / version 等标识只作为后端返回的展示事实，不在前端自行拼接权限关系。

## 测试

新增 `frontend/tests/views/WorkflowLifecycle.test.ts`，覆盖：

- Workflow / Version / Trigger / Scheduler / Execution 联动展示；
- 中文生命周期状态；
- 无工作流空状态。

本切片属于单一功能原子提交；本地 Frontend Gate 仍需在开发环境执行后记录实际结果，不能以 GitHub Actions 代替本地验收。
